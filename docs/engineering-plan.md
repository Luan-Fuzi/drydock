# 工程准备与测试策略

2026-09-27 定稿。原则：**丢弃型原型阶段，测量仪器建精，脚手架从简**。判断一项准备是否现在做，看两个条件任一成立：它让 Q1/Q7 的结论更可信；它能被产品化阶段（阶段 2）直接继承。本文按四个领域给出"原型期做 / 产品期做"的切分。

## 1. 性能测试探针（原型期核心投资）

原型的存在目的是产出数据，探针就是产品。

### 环境内基准电池（服务 Q7）

- 工具：`hyperfine`，固定数据集与固定参数，结果输出 JSON 落盘。
- 用例：`npm install`（create-vite 模板）、`tar` 解包（同一 500 MB 压缩包）、stat 风暴（`find` 全树 + node 启动）、`make -j$(nproc)`（小型 C 项目）。
- 对比维度：翻译引擎（proot Termux fork / proroot / proot+seccomp 关）× 每用例至少 5 次取中位数。
- 数据进 Q7 的选型结论，不进营销文案。

### 宿主侧存活遥测（服务 Q1）

前台服务内建时间线记录器，事件包括：锁屏/解锁、WakeLock 获取释放、前台服务重启、proot 进程退出码、tmux 会话心跳（每 60s）、CPU 温度与频率采样（每 5min）、充电状态。本地 ring buffer，调试菜单一键导出报告。

判据表（与 open-questions Q1 对齐）：

| 编号 | 判据 | 通过线 |
|---|---|---|
| S1 | 锁屏 30 分钟后任务仍存活 | 全部样本通过 |
| S2 | 系统杀进程后 tmux 可接回、任务未丢 | 全部样本通过 |
| S3 | 持续负载下发热与降频可接受 | 表面温度与频率曲线人工评估 |

## 2. 测试策略（原型期定义方法，产品期铺开覆盖）

### 原型期

- **单元测试只覆盖会进产品的纯逻辑**：翻译引擎的参数拼装、端点预设模板渲染、成果落袋规则、镜像源选择逻辑。一次性胶水代码不写测试。
- **重点形态是"验收剧本"（AV）**，每条 = 可重复脚本 + 通过判据，跑真机：
  - AV1 冷启动：装 APK → 拉 rootfs → shell 提示符，全程 ≤ 15 分钟；
  - AV2 终端链路：ttyd WebSocket 连通，xterm.js 渲染与键盘输入正常，中文输入不乱码；
  - AV3 agent 链路：npm 下载 Claude Code → 配 GLM 端点 → 完成一次对话并产出文件；
  - AV4/S1、AV5/S2：存活判据（对应探针）。
- **CI**：GitHub Actions；arm64 runner 构建 rootfs 与 APK（DSHA 已验证此形态），跑构建 + 剧本冒烟。不设覆盖率门禁。

### 产品期（阶段 2）

覆盖率门禁、OEM 机型回归矩阵、Claude Code hooks 适配器的契约测试、遥测数据回归基线（每个版本对比性能不退化）。

## 3. 安全（原型期做威胁模型与不变量，工具扫描留到产品期）

### 威胁模型（一页，现在写）

- **资产**：API key、用户代码与会话内容、环境完整性。
- **攻击面**：localhost WebSocket 端口（安卓上同机其他 App 可访问）、环境内任意脚本（`curl | bash` 类）、SAF 暴露的文件树、npm/rootfs 供应链。
- **信任边界**：proot 是视角欺骗不是隔离（六类方案分析已确认，proot 与 proroot 同级无隔离），**环境按不可信域对待，密钥相关设计以此为前提**。

### 安全不变量（现在定为设计约束，产品期逐条验收）

| 编号 | 不变量 |
|---|---|
| I1 | API key 只存 Android Keystore；按进程注入环境变量；永不写入环境内文件系统 |
| I2 | ttyd/WebSocket 绑定随机 token，每次启动轮换；仅监听 localhost |
| I3 | DocumentsProvider 只暴露环境内项目目录，不暴露宿主私有路径 |
| I4 | 成果落袋为单向写入 `/sdcard`，不对该目录内容做执行或回读解析 |
| I5 | rootfs 与 agent 安装包经哈希/签名校验后方可使用；校验失败拒绝执行 |
| I6 | LAN 访问类功能（若做）默认关闭，开启需显式授权 |

### 工具化（产品期接 CI）

依赖审计（npm audit / lockfile 审计）、Android Lint、APK 静态扫描、密钥泄漏扫描。

## 4. 前端设计风格（原型期定语言，产品期做系统）

原型 95% 界面是终端视图，设计决策很少，现在只锁定语言级决策，避免阶段 2 各处不一致：

- **基底**：Material 3（安卓用户熟悉，DroidSpaces/DSHA 同款基底）；深色优先。
- **终端区零装饰**：xterm.js 原生观感，宿主 UI 只围绕它存在，不覆盖、不美化终端内容。
- **状态语义色**（全产品唯一允许的强色）：运行中 / 等待批准 / 空闲，三色贯穿状态灯、通知、抽屉。
- **产出物**：一页 design tokens（色板、字号阶梯、间距、圆角）+ 五个核心组件的规格——状态灯、批准卡片、虚拟键条、会话抽屉、成果面板。

阶段 2 再扩为完整设计系统与组件库。

## 5. 开发回路与反馈面

反馈速度匹配迭代频率：环境层脚本改动最频繁 → `adb push` + `am` 重启服务免编译（debug 包经 `run-as` 可进私有目录）；WebView 终端层 → `chrome://inspect` 从 Mac 直调手机 WebView 的完整 DevTools（渲染、WebSocket 帧、console）；宿主 App → JVM 单测秒级（纯逻辑）+ `installDebug` 十秒级（整机）；产品判据 → 真机遥测（Q1）与基准电池（Q7）、AV 剧本一条命令重跑。CI 挂 AV 冒烟，每次提交自动确认未跑偏。
